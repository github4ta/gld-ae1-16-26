# Памятка для ревьюера (Code Review Guidelines)

Цель ревью — не придраться к стилю, а убедиться, что код работает без скрытых багов, соответствует ТЗ и не сломает ветку `develop` другим разработчикам.

---

## Этап 1. Формальная проверка (до чтения кода)

Если не выполнен хотя бы один пункт ниже, сразу отклоняйте PR (**Request Changes**) без глубокой проверки:

* **Ветка назначения:** PR открыт строго в `develop` (а не в `main`).
* **Конфликты:** В интерфейсе Git отсутствует предупреждение о конфликтах слияния (*Merge conflicts*).
* **Описание PR:** Заполнены номер задачи (`GD-XXX`), чек-лист и приложен скриншот или текст вывода из консоли (для задач с выводом).
* **Чистота диффа (Files changed):** В PR нет системных файлов IDE (`.idea/`, `*.iml`, `.vscode/`) и скомпилированных классов (`target/`, `out/`).

---

## Этап 2. Проверка по эпикам (типовые баги и «ловушки»)

### 1. При проверке моделей данных (Эпик 0: `GD-001` — `GD-006`)
* **Инкапсуляция:** У всех полей классов стоит модификатор `private`.
* **Защита от `NullPointerException`:** В конструкторах без параметров у классов-контейнеров (`CatalogItem`, `CatalogSubcategory`, `CatalogCategory`, `Cart`) поля списков инициализированы пустой коллекцией (`new ArrayList<>()`), а не оставлены `null`.
* **Имена и пакеты:** Названия пакетов (`by.green.dostavka.catalog`, `by.green.dostavka.cart`) и полей (`items`, `subcategories`, `products`, `amount`) совпадают с ТЗ до буквы.

### 2. При проверке наполнения данными (Эпик 1: `GD-101` — `GD-104`)
* **Потерянный код при слиянии:** Если автор разрешал конфликт в `Main.java` после слияния веток фруктов и овощей, проверьте, что он случайно не удалил кусок кода коллеги.
* **Перепутанные коллекции:** Убедитесь, что в `catalogItemApple` добавлен список `apples`, а не `pears` (частая ошибка при копипасте).

### 3. При проверке утилиты форматирования (Эпик 2: `GD-201` — `GD-205`)
* **Конкатенация в цикле:** Если внутри `for` используется `result += ...` вместо `StringBuilder`, отправьте на доработку.
* **Сломанная табуляция в `getCatalogSubCategoryAsString` (`GD-204`):**
    * *Частый баг:* Разработчик вызывает `sb.append("\t").append(getCatalogItemAsString(item))`. В итоге табуляция сдвигает только заголовок группы (`ЯБЛОКО:`), а список продуктов под ним прилипает к левому краю.
    * *Как должно быть:* Все переносы `\n` внутри вложенного блока должны быть заменены на `\n\t`, чтобы продукты имели двойной отступ `\t\t`.
* **Лишний перенос в конце:** В конце итоговой строки не должно быть висящего `\n`, иначе при выводе в консоль между блоками появляются лишние пустые строки.
* **Регистр заголовков:** Названия `CatalogItem` и `CatalogSubcategory` должны выводиться в верхнем регистре (`.toUpperCase()`).

### 4. При проверке логики корзины и чека (Эпик 3: `GD-301` — `GD-303`)
* **Артефакты плавающей точки:** При умножении `double` (например, `6.99 * 3`) Java может выдать `20.970000000000002`. Проверьте, что автор округлил итоговую сумму при выводе (например, через `String.format("%.2f", total)`).
* **Пустая корзина:** Мысленно прогоните метод `getCartCheckAsString()` на пустом списке `items`. Он должен вернуть строку `"ВАША КОРЗИНА:"`, а не упасть с ошибкой.
* **Забытый отладочный код:** В `Main.java` не должно остаться временных `System.out.println("test")` или закомментированных блоков.

## Этап 3. Правила хорошего тона при оставлении комментариев

* **Не пишите просто «Неправильно» или «Переделай».** Объясните *почему* это проблема и *какой результат* ожидается.
    * *Плохо:* «Тут кривые отступы».
    * *Хорошо:* «В методе `getCatalogSubCategoryAsString` табуляция применяется только к первой строке группы. Замените `\n` на `\n\t` для всего блока `CatalogItem`, чтобы продукты сдвинулись на второй уровень вложенности».
* **Разделяйте критичные замечания и советы:**
    * `[Blocker]` — баг, нарушение ТЗ, некомпилируемый код (мержить нельзя).
    * `[Nitpick / Minor]` — мелкое улучшение стиля или нейминга (можно поправить при желании, не блокирует слияние).
